# XSBench_intel_sharedDB

*Same Monte Carlo cross-section lookup kernel as `XSBench_intel`, but the
nuclide/energy grid is held as a handful of large contiguous DBs shared
(read-only) by every worker "thread" of a rank, instead of exploded into one
DB per grid item — and this port is genuinely SPMD, with each rank pinned to
its own node.*
Source: `third_party/ocr-apps/apps/XSBench/refactored/ocr/intel-sharedDB/src/`
(`Main.c`, `io.c`, `GridInit.c`, `CalculateXS.c`, `XSutils.c`, `Materials.c`,
`timers.c`).

## Overview

Computes the same H-M reactor cross-section lookup workload as
`XSBench_intel`, but structured as `-p` independent SPMD "ranks", each
forked via `forkSpmdEdts_Cart1D` and pinned to one ARTS node through the OCR
affinity extension. Each rank independently *regenerates its own full copy*
of the nuclide/energy grid — there is no cross-rank sharing of grid content.
The "sharedDB" in the name is intra-rank: the grid is a handful of large
contiguous DBs (one nuclide-grid DB, one unionized-energy-grid DB, one
flattened cross-section-index DB, ...) that every one of that rank's `-t`
worker "threads" reads concurrently, in contrast to `XSBench_intel`'s
per-item DB fan-out. Lookups are not exploded into per-lookup EDTs either:
each worker processes a large contiguous chunk of lookups inline, in a
straight-line C loop inside one EDT.

The result scalar is `XS Checksum: <u64>`, a computed digest of the lookup
phase: every compute task sums `|macro_xs[0..4]|` over its own lookups, in its
own order, and adds one magnitude-quantized contribution to its chain's `u64`
digest; `summaryEdt` folds the chains by integer add. The fold is
order-independent, so the value does not depend on completion order, on which
worker ran a chain, or on the node count. It is a pure function of
`(-s, -g, -l, -t)` and of nothing else — not of `-p`, not of the geometry —
which makes the campaign pin checkable in seconds on one node. It covers
instance 0's chains; instances 1..31 compute their own digests but do not
appear in the printed value (bringing them in would need a second cross-rank
collective, and this row's identity is that it has exactly one cross-rank
edge). The `Workload    (unit): <lookups>` line printed by the shared
`print_throughput_custom` helper is still there and is still a plain echo of
`-l`; it is the completion marker, not the scalar.

**Sensitivity of the digest, stated in checkable terms.** The quantum is
applied to a whole task's chunk sum, not to a lookup: `xs_quantize` keeps 20
mantissa bits of the sum of `5 × CHUNK_SIZE` addends (5000 at the campaign
grain; the last generation's chunk may be shorter). So the digest moves only on
a divergence larger than roughly `2^-20` of that chunk sum — order 0.5% of a
single lookup's contribution at the campaign grain — and is blind below it. It
is a cheap detector of gross corruption, a wrong dataset, a dropped or
duplicated range, and a wrong node-count-dependent result; it is **not** a
last-bit oracle and must not be quoted as one. The trade is deliberate: the
chunk-sum quantum is what makes the same number come back from three separately
built runtimes whose arithmetic may differ in the last bits. Quantizing per
lookup instead would buy `2^-20`-per-lookup sensitivity for about one `frexp`
per lookup, at the price of that cross-build robustness — recorded as an open
choice, not taken here.

The data the digest is taken over is generated by a counter-based mixer keyed
by `(instance, stream, position in the array)` — no `rand()`, no `srand()`, no
shared generator state, and identical at every node count and in every run.

## Structure

Let `N_i`, `N_g`, `N_m=12`, `L` as before, `P` = nprocs, `T` = nthreads,
`U = N_i·N_g`, `G = ⌈L / (1000·T)⌉` (generations per thread-chain) and
`A = min(T, U)` (producers in the unionized-grid alignment fan-out).

| object | count | size |
|--------|-------|------|
| Per-rank scaffolding EDTs, incl. `mainEdt` itself (`mainEdt`→`initEdt`→`channelSetupEdt`→`FNC_xsbenchMain`→`FNC_initSimulation`→`alignJoinEdt`→`lookUpKernelEdt`→`launchReductionEdt`→`summaryEdt`) | `1 + 8·P` | — |
| `alignGridEdt` (init fan-out: one per disjoint unionized-grid row range) | `A·P` | — |
| `lookUpKernelPerThreadEdt` + `iterationsPerThreadEdt` (one pair per thread-chain generation) | `2·P·T·G` | — |
| Top-level (`wrapUpEdt`) | 1 | — |
| **EDTs total** | `2 + P·(9 + A) + 2·P·T·G` | — |
| Per-rank "handle" DBs (rankH, rankDataH, rpPerfTimer, the 6 grid/material DBs, 3 pointer-array DBs, **plus 2 more from the nested `gpmatrix` call inside `generate_energy_grid`'s own unionized-grid sort, plus one created inside `reductionLaunch`**) | `15·P` at `P=1`; the reduction tree adds a small number of further per-rank DBs once `P > 1` | grid DBs scale with `N_i·N_g`; the rest are small |
| Per-chain scratch DBs (`DBK_seed` 8 B, `DBK_xs` a 48-byte `LaneResult` = the last lookup's 5 cross sections + the chain's digest; created once per tid, reused across generations, destroyed by `summaryEdt`) | `2·P·T` | tiny |
| Alignment output blocks (one per `alignGridEdt`, destroyed by `alignJoinEdt` once copied into `xs_grid`) + the pointer table each producer rebuilds and destroys | `2·A·P` | the output blocks sum to exactly one `xs_grid` (`N_i·U·4` per instance) and are alive only during init |
| Per-generation ephemeral pointer DBs (created and destroyed within each `iterationsPerThreadEdt`) | `3·P·T·G` | tiny |
| Top-level (`argv`, `globalParamH`) | 2 | small |
| **DBs total** | `2 + P·(15 + 2·A + 2·T + 3·T·G)` | — |
| Events (`mainEdt`'s `finalOnceEVT`, per-rank `rpPerfTimerEVT`/`loopCompletionLatchEVT`, 2 per alignment producer — its output event and the `COUNTED` relay the join registers on — and 3 per thread-chain generation) | `1 + P·(2 + 2·A) + 3·P·T·G` | — |

`generate_energy_grid` (`GridInit.c`) calls `gpmatrix` a *second* time
internally to build a temporary sorted copy of the nuclide grid before
destroying it (`DBK_nuclide_grids`/`DBK_nuclide_grid_ptrs`, immediately
`ocrDbDestroy`'d — `NUM_DB_CREATE` counts the create regardless), so
`initSimulation`'s own DB fan-out is 11 creates (`gpmatrix`×2 +
`generate_energy_grid`'s own `uEnergy_grid`/`xs_grid` + `load_num_nucs` +
`load_mats`×2 + `load_concs`×2), not the 9 the original count assumed. Each
generation's 3 events are `iterationsPerThreadEdt`'s FINISH-scoped output
event pair (`ocrEdtCreate(...,EDT_PROP_FINISH,...,&iterationsPerThreadOEVT)`
→ output + finish) plus `createEventHelper`'s `OCR_EVENT_COUNTED_T` join —
the original `2·P·T·G` term missed the third.

Smoke-sized example (`-s small -g 10 -l 100`, `P=T=1`): `N_i=68`, `N_g=10`,
`U=680`, `G=⌈100/1000⌉=1`, `A=min(1,680)=1`. EDTs ≈ `2+(9+1)+2 = 14`.
DBs ≈ `2+(15+2+2+3) = 24`. Events ≈ `1+(2+2)+3 = 8`. The dominant DB is `DBK_xs_grid` at `N_i·U·4 B`;
`DBK_nuclide_grids` and `DBK_uEnergy_grid` are each allocated at `U·48 B`
(`DBK_uEnergy_grid` is allocated at `NuclideGridPoint` size — 48 B/point —
but indexed as the 8-byte energy-only `GridPoint`, so 5/6 of that buffer is
never addressed; harmless, just wasted, and left as published). At the
calibrated `-s large -g 96 -p 32 -l 176000000 -t 216`, one
instance holds `U = N_i·N_g = 34080`, `xs_grid` ~48 MB (well out of cache) and
the grids ~1.6 MB each; the compute plane is 32 instances × `T` chains ×
`G = ⌈L/(1000·T)⌉` generations — coarse-grain (1000 inline lookups per
generation EDT), in contrast to `XSBench_intel`'s per-lookup 3-EDT chains, and
identical at every node count.

Counter cross-check: the recorded check (1 node, `-s small -g 3 -l 100` vs
`-s small -g 5 -l 2500`, predicted absolutes 13/23/6 and 17/29/12 for
`NUM_EDT_CREATE`/`NUM_DB_CREATE`/`NUM_EVENT_CREATE`, against a runtime
baseline of `+1 EDT, +1 DB, +0 EVT`) was taken at `P=T=1`, where the reduction
tree degenerates, so it never exercised the `P`-dependence of the reduction
library's own creates. **The formulas changed this cycle** — the alignment
fan-out adds `A+1` EDTs, `2·A` DBs and `2·A` events per instance — so the
recorded absolutes are void and the check must be re-taken (and re-taken with
`-p 2` if a per-rank constant is wanted at `P > 1`).

## Wiring

`iterationsPerThreadEdt` is the sole reader of the grid: one EDT per
(rank, thread, generation) holds RO (`DB_MODE_RO`) deps on six DBs —
`nuclide_grids`, `uEnergy_grid`, `xs_grid`, `num_nucs`, `mats_all`,
`concs_all` — plus RW on its own private per-chain `seed`/`LaneResult`
scratch, and performs its entire `[ibegin,iend]` lookup range as one
straight-line C loop with `calculate_macro_xs`. No further EDT fan-out per
lookup, and **no shared accumulator anywhere in the lookup phase**: the
digest is written only into the chain's own scratch DB, so no generation
acquires anything exclusively.

Max concurrent RO readers on one rank's grid DB is `T` (bounded by how many
thread-chains run concurrently within that rank); ranks never share a DB
instance (each rank privately regenerates its own grid), so cross-rank
concurrency does not compound onto one DB object — it instead multiplies
memory footprint by `P` (each rank pays the full grid cost independently, as
opposed to `XSBench_intel`'s single shared grid). No DB is ever taken RW by
more than one node's tasks: init writes are single-writer, and the per-chain
scratch DBs and per-generation pointer DBs are private and never contended.
The contention point is the rank's large `xs_grid`/`nuclide_grids` DBs under
`T`-way concurrent RO acquire at the start of each generation: at the
campaign's `-t 216` that is a 216-way RO fan-in on one rank's 48 MB grid,
`G` times per instance, and it is the only per-rank coherence pressure the row
has.

The one cross-rank data dependency in the whole program is
`launchReductionEdt` → `reductionLaunch`, a labeled-GUID `ALLREDUCE`
(`REDUCTION_F8_MAX`) over the `P` ranks' elapsed times, feeding the printed
throughput and gating shutdown. Everything else is node-local apart from a
one-shot broadcast: `argv` and `globalParamH` are created on rank 0 and
RO-acquired once by each instance's `initEdt`.

The alignment fan-out that fills `xs_grid` is the one other multi-EDT
structure, and it is init: `A` `alignGridEdt` producers each hold RO on
`nuclide_grids` and `uEnergy_grid` and RW on **its own** output block, and one
`alignJoinEdt` holds RO on all `A` blocks plus RW on `xs_grid` and copies them
into place. No two tasks ever write the same datablock, so this phase is
DB-WRF-valid as well as OCR-legal, and the RO fan-in on
the two grid DBs during init is the same shape as the kernel's.  (The row is
outside DB-WRF overall on the creator-held hand-offs the catalog records, not
on this alignment fan-out.)

`summaryEdt` additionally holds one RO dependence per chain scratch DB and per
chain seed DB (`3 + 2·T` deps in total): that is how the per-chain digests
reach the printing task, and it is where the `2·P·T` chain datablocks are
destroyed. The fan-in is node-local and happens once, after the reduction.

## Flow

Per rank: `initEdt` (pinned to its node) → `channelSetupEdt` →
`FNC_xsbenchMain` → `FNC_initSimulation` → `A` × `alignGridEdt` →
`alignJoinEdt` → `lookUpKernelEdt` spawns `T`
independent generation-chains (and creates `summaryEdt`, which can only be
wired once the chains' datablocks exist) → `launchReductionEdt` (waits on a
`LATCH` event gated by all `T` chains reaching their last generation) →
`summaryEdt` → top-level `wrapUpEdt` shuts down. Each chain's last generation
releases its scratch DB before decrementing the latch, so its digest is
published ahead of the signal that eventually admits `summaryEdt`.

`FNC_initSimulation` runs `gpmatrix` / `generate_energy_grid` / `load_mats` /
`load_concs` straight-line in C and then **fans the unionized-grid alignment
out**. That alignment is `U·N_i` binary searches — by far the largest init term
and the one that used to run single-threaded inside the one init EDT (~0.4-1.0 s
per instance, constant in node count, i.e. order 15% of a projected 32-node
cell). It is independent over the `U` rows, so it is now produced by `A` tasks
over disjoint row ranges, each writing its own output block, and assembled by
one `alignJoinEdt` whose only serial term is a `N_i·U·4`-byte copy (order 5 ms
against the ~300+ ms it replaces). The join is what creates `lookUpKernelEdt`,
so the lookup phase starts only once the whole index is in place, and the app's
own `total_timer` is started there — the alignment sits, as before, outside the
reported simulation time but inside the `[E2E]` window that the campaign
measures. Grid *generation* is likewise no longer a shared-state term: it is
keyed per position, lock-free, and runs concurrently in every co-resident
instance. What remains serial in init is the sorting (`N_i` per-nuclide
`qsort`s and one `U`-element `qsort`), which is `O(U log U)` and one to two
orders below the alignment it feeds.

Compute-phase parallel width is `P·T` (assuming ranks run concurrently, and
each rank's `T` chains run concurrently); within a chain, generations are
strictly serial (each `lookUpKernelPerThreadEdt` gates the next on its
predecessor's `FINISH` scope draining) — `G` sync points per chain, same
batching structure as `XSBench_intel`'s `NB` but over coarse per-thread
chunks (`CHUNK_SIZE=1000`) rather than per-lookup fan-out.

## Placement (base)

Unlike `XSBench_intel`, this port makes real, non-`NULL_HINT` placement
decisions. `forkSpmdEdts_Cart1D` pins each of the `P` rank-init chains to a
specific ARTS node via `OCR_HINT_EDT_AFFINITY`, computed by a **block**
partition of the `P` ranks over `ocrAffinityCount(AFFINITY_PD)` nodes (rank
`i` → a contiguous block, not round-robin). Confirmed against the shim:
`AFFINITY_PD`'s count is `arts_get_total_ranks()`, and the hint value is
consumed directly as an ARTS rank id (`extract_edt_affinity` in
`benchmarks/ocr_shim/arts_ocr.c`). Every DB and EDT a rank creates thereafter
inherits that rank's captured `myDbkAffinityHNT`/`myEdtAffinityHNT`
(`getAffinityHintsForDBandEdt`, itself reading `ocrAffinityGetCurrent` — "the
node I'm running on right now") — so a rank's grid, materials, and lookup
EDTs are co-located on one node by construction: real locality, unlike
`XSBench_intel`'s scatter. The single exception is the top-level `wrapUpEdt`,
created with `NULL_HINT` and therefore placed by runtime round-robin; it only
prints and calls `ocrShutdown`.

`-p` is fixed at 32 in the catalog and is **not** scaled to the node count:
the sweep invariant is the strict one, the same 32 instances at every
geometry, and the fork's block partition packs `32/N` of them onto each of the
`N` nodes (every campaign node count divides 32, so load imbalance is exactly
1.000 at 2, 4, 8, 16 and 32 nodes). Running with `-p` below the node count is
refused at startup: it would leave nodes with no instance while the sweep
still looked complete.

## Placement (hinted) — tried on paper, none beats the base

Audited 2026-09-08 from source rather than assumed: the attempt here is the
enumeration itself, since every candidate map turns out to be the base's own
placement or provably negative, so there was nothing left to measure.  A `NULL_HINT` datablock
is creator-homed in the shim (`arts_ocr.c`, `ARTS_SHIM_NOHINT_DB_HOME` =
CREATOR), so a hint-less DB created inside a pinned EDT is already homed on
that EDT's node; every EDT except the final `wrapUpEDT` carries the affinity
captured in the fork-pinned `initEdt`.  Every create — top level, per
instance, per lane, per generation, wrap-up — is tabulated in the audit unit
(`units/hinted-review/nohint-XSBench_intel_sharedDB/FINDING.md`).  The
freedoms, all inert: the instance→node map (instances share no DB and no
event, so any bijection is the identity up to relabelling; the block map even
wins the one tie-break, putting instance 0 where `finalOnceEVT` lives); a
per-lane DB affinity (strict identity with creator-home — the analogue of the
RSBench_intel_sharedDB layer, which was found identical there too, is identical
here in both of its halves, since this port has no per-lane policy-domain
substitution to undo); the two rank-0 broadcast blocks (32 readers on N nodes,
no single home helps); `wrapUpEDT` (≤ 1 message per run); spreading the align
fan-out or the grids (arithmetically negative — no idle node exists and the
grids would turn 5.6×10⁹ local reads remote).

Cross-node data flow in the measured window: zero per lookup and per
generation EDT (all ten dependences instance-local — 56 M acquires, every one
a local hit); per instance two RO acquires of the rank-0 broadcast blocks
(≲ 1 KB); per run one `REDUCTION_F8_MAX` ALLREDUCE over 32 participants, 62
edges of 8 bytes.  Whole-run budget at 32 nodes: 124 cross-node dependence
edges, ≈ 32 KB, `2.2×10⁻⁶` of the local acquires; deleting all of it would buy
~4 ms of a 98.5 s anchor.  No static map can beat the base's, so the base
stands in for the hinted comparison — hinted was tried, on paper, and lost.

## Sizing (measured)

Every input is fixed at the largest geometry's calibration and held across
the node sweep (the campaign convention, shared with the tiled rank grids):
`-p 32` instances, `-t 216` chains each, `-l 176000000` per instance (see
below). `-l` is **per instance** (each instance is an independent MC replica),
so aggregate work is `32 × L`; `-g`/`-s` scale the per-instance replica and
its one-time init, replicated 32 times. At 32 nodes the fork's block partition
puts one instance per node; at fewer nodes the same 32 instances pack evenly.

`-t` is a logical chain count, not a thread count — nothing an app passes
can change the runtime's rank or worker count. `-t 108` would follow the
campaign's SPMD width rule at the calibration geometry with width `P·T =
3456`, exactly 1× the 32-node worker count, one chain per worker at 32
nodes. The knob is real and measured (`-t 1` → 2.55M lookups/s single-chain,
`-t 15` on 15 workers → 28M/s; widths from 15 to 3456 on 15 workers measure
within noise of each other), so the catalog's `-t 216` (width 6912 = 2×)
costs nothing structurally — `G` absorbs it and no object count changes —
and `-p 64` with half the `-l` would reach 2× the other way at the same
aggregate.

**Three changes make every previously recorded number for this row void.** The
port originally kept a pointer field (`xs_ptrs`) inside the shared
unionized-grid DB and had every generation EDT re-derive it — ~544 KB of
identical-value stores into RO-acquired memory per generation, because a DB's
mapping is acquire-relative. Those concurrent same-line stores ping-ponged
across NUMA domains and froze per-worker scaling (9.1M lookups/s at 15 workers
≈ 10.4M/s at 108). The field is gone — the kernel indexes the flat `xs_grid`
arithmetically — and the wall went with it: 20.1M/s at 15 workers, **131.5M/s
at 108** (91% per-worker efficiency, `-g 1000` small), 2.2× and 12.6× over the
pointer-fixup form. The *second* rebuild of the same kind is now gone too:
`assignNuclideGridPtrs` reconstructed the `N_i` row pointers once per compute
task with an `O(N_i·N_g)` loop carrying a runtime-divisor modulo — 34,080
integer divisions to store 355 pointers, order 0.3 ms against a task body of
order 0.8 ms — and is now the `O(N_i)` form with identical output. Both apply
to arts, xsocr and ocr-vx from the one source. Third, the unionized-grid
alignment moved out of the single init EDT into an `A`-way fan-out, removing a
constant ~0.4-1.0 s per instance from every cell. Together with the changed
dataset (keyed generation), the one-node anchor is measured at 98.5 s
(`-l 176000000 -t 216 -p 32`); the node-count trend above predates all three
changes and is what a fresh campaign sweep re-takes.

`-g` sets the table size and thus how memory-bound the inline kernel is; at
the calibrated `-s large -g 96` the kernel ran ~1.2-1.3 µs/lookup at 15
workers (14.8M/s) *before* the pointer-rebuild repair. `-g` is capped by this
decomposition rather than chosen: at the published `-g 11303` one instance
holds 5.70 GB of `xs_grid` alone, so 32 replicas need ~195 GB against a 190 GB
per-node budget, and the alignment would run 1.42G binary searches per instance
(now spread over `A` producers, but 12× the work). With the size knob capped,
the E2E window is reached with `-l`, which is this row's one unavoidable knob
deviation.

**Memory per instance** (independent of `-l` and `-t`), with `U = N_i·N_g`:
`nuclide_grids` `U·48 + N_i·8`, `uEnergy_grid` `U·48` allocated (`U·8`
addressed), `xs_grid` `N_i·U·4`, a transient sorted copy `U·48` during init
only, materials ~6 KB, and — during the alignment phase only — one further
`N_i·U·4` in the `A` producer output blocks, which the join copies into
`xs_grid` and destroys. At `-s large -g 96`: **~101.7 MB peak (during
alignment), ~51.7 MB steady**, so `-p 32` is **3.25 GB** at the init peak and
**1.65 GB** of steady payload, plus `P·T·56 B` of chain scratch and at most
three ~3 KB ephemeral pointer DBs per running task; the catalog's measured
resident set is now **9.1 GB**, taken after the fan-out (the previous
**7.5 GB** predates it). Even the init peak is under 4% of the 190 GB
one-node budget.

**Cache residency at the top of the sweep.** The random-access target is
`xs_grid`, 48.4 MB per instance, and the per-node footprint is `32/N · 51.7 MB`
— 1.65 GB / 828 / 414 / 207 / 103 / 52 MB at 1/2/4/8/16/32 nodes. Against a
socket LLC of order 100 MB the workload becomes cache-resident between 8 and 16
nodes, so the per-lookup cost falls there for a reason that is not the runtime.
Raising `-g` would remove the artifact but is blocked by the set convention
that both XSBench rows run the identical physics table and by the sibling's
`-g`-bound init wall, so it is disclosed instead. It pushes the top of the
curve **up**, and with the alignment fan-out in place there is no longer a
serial init floor pushing it the other way: read 16n/32n with the residency
artifact named.
