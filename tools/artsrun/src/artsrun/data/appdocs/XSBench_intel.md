# XSBench_intel

*Monte Carlo cross-section lookup proxy (ANL) — the grid is exploded into one
DB per nuclide and one DB per unionized energy gridpoint; every lookup is a
3-EDT chain touching a handful of those DBs.*
Source: `third_party/ocr-apps/apps/XSBench/refactored/ocr/intel/src/`
(`Main.c`, `io.c`, `CalculateXS.c`, `XSutils.c`, `Materials.c`, `qsort.c`,
`timers.c`; ~1300 lines, mostly `Main.c`).

## Overview

XSBench is a proxy for the macroscopic-cross-section lookup kernel at the
heart of Monte Carlo neutron-transport codes (the OpenMC family). The program
builds a Hoogenboom-Martin (H-M) reactor's per-nuclide microscopic
cross-section energy grids, unions them into one grid, then issues `-l`
randomized lookups: pick an energy and a material, binary-search the
unionized grid, and for every nuclide in that material interpolate a 5-vector
of cross sections. Every lookup's numeric result is computed and then
discarded — this port does not verify the lookup arithmetic.

The grids are generated by one task per nuclide from an index-seeded
generator: every value is a pure function of `(stream, (nuclide, gridpoint,
field))`, drawn with the `rn_indexed`/`xs_grid_index` pair in the shared
header `refactored/ocr/xs_index_rng.h`, so no generator state is carried
between elements and the table does not depend on the number of tasks, places
or nodes that produce it. The material concentrations come from the same
header on a second stream (`rn_indexed`/`xs_conc_index`, a pure function of
`(material, element)`). The restructured tier includes that header too, so all
three tiers build the identical table from the same `-s`/`-g`.

The result scalar is `XSBench grid checksum: <u64>`, printed once by the
task that unions the generated grids: the sum of the IEEE-754 bit patterns of
the unionized energy grid's values. The sum is exact and commutative, so it is
a function of the multiset of generated energies — independent of `-l`, `-b`,
the node count, the arm and the completion order, and moving only with
`-s`/`-g`. It is exactly what the catalog's `expect` checks — it proves the
grid was built identically, not that any lookup computed the right answer. The
same line is printed by the restructured tier (`XSBench_intel_dist`, an
`extra_scalars` entry there) at place 0, over the same domain, so at equal
`-s`/`-g` the two rows must print the **same value**; that equality is the
cross-tier oracle. The `expect` pin is `3906729473756589834`, taken from the
first successful cell after the generator changed to index-seeded
generation; the previous value no longer applies.

This layout — one DB per nuclide grid and one DB per unionized-grid point,
each lookup expanding into an independent 3-EDT chain, everything placed with
`NULL_HINT` — makes the program a stress test of task-creation churn and
fine-grain DB creation/RO-acquire traffic; there is negligible floating-point
work per task. Contrast `XSBench_intel_sharedDB`, which holds the same grid
as a handful of large DBs instead — a separate catalog row at its own
problem instance (32 instances × 176,000,000 lookups), not this row's
restructured tier. Whether this row carries a restructured tier is the
catalog's to state, and the position is in flux: the standing catalog text
says any distribution-friendly rebuild converges on that sibling, while
`experiments/benchsets/paper-main.yaml` says the tier is held back until its
source lands — and a source tree for one
(`third_party/ocr-apps/apps/XSBench/refactored/ocr/intel-dist/`, appdoc
`XSBench_intel_dist.md`) now exists and shares this row's generator header, so
the two build the same table. Read the catalog row, not this paragraph, for
the tier that actually runs.

## Structure

Let `N_i` = n_isotopes, `N_g` = n_gridpoints, `U = N_i·N_g` (unionized grid
points), `L` = lookups, `NB = ⌈L / b⌉` (compute-phase sync batches, `b` =
`-b`; the calibrated args use `b=6912`, `L=2,764,800` → `NB=400`).

| object | count | size |
|--------|-------|------|
| Nuclide grid DBs | `N_i` | `N_g × 48 B` each (6 `double`s) |
| Unionized-gridpoint DBs (`uEnergy_grid[i]`) | `U` | `N_i × 4 B` each (per-point nuclide index array) |
| Material DBs (index list + concs list) | `2 × 12 = 24` | varies (`num_nucs[mat]×4 B` / `×8 B`) |
| Scaffolding/handle DBs (Inputs, rank/data handles, array-of-GUID holders, timers) | 17 | small |
| **DBs total** | `41 + N_i + U` | — |
| Init-phase scaffolding EDTs, incl. `mainEdt` itself | 17 (fixed) | — |
| `init_grids_i` (grid generation + per-nuclide sort, one per nuclide grid DB) | `N_i` | — |
| `init_uEnergy_i` (grid-alignment binary searches, one per unionized point) | `U` | — |
| `rankCompute` / `rankMultiLookupSpawner` (sync-batch pair) | `2·NB` | — |
| `rankLookup` / `macroxs` / `microxsAggregator` (one chain per lookup) | `3·L` | — |
| **EDTs total** | `17 + N_i + U + 2·NB + 3·L` | — |
| **Events total** | `27 + 3·NB` | — |
| EDT templates | 3 persistent (`rankLookup`/`macroxs`/`microxsAggregator`), created once and reused for every lookup — no per-lookup template churn | — |

The 17 fixed EDTs are `mainEdt` (the shim materializes it as its own EDT,
distinct from the runtime's own bootstrap wrapper — see the cross-check note
below) plus the 16-deep scaffolding chain
(`globalInit`→`init_InputsH`→`rankInitSpawner`→`rankInit`→`init_InputsH`→
`init_rankH`→`init_dataH`→`init_gridsSpawner`→`init_uEnergy_union`→
`init_uEnergy`→`init_materials`→`globalCompute`→
`globalComputeSpawner`→`globalFinalize`, plus `timer`) that runs regardless of
`nprocs` (hardcoded to 1, so none of this chain's own loops contribute a
second factor). The event total's `27` fixed events are the output/finish
events the accounting rule attaches to those same 17 EDTs (`mainEdt`'s four
FINISH-scoped children `settingsInit`/`globalInit`/`globalCompute`/
`globalFinalize` alone contribute 4 explicit STICKY events + 8 output/finish
events) plus the always-present `init_InputsH`/`globalComputeSpawner`/`timer`
output events, the `init_dataH`-spawned `init_uEnergy`/`init_materials`
finish events, and the two init join points: `init_gridsSpawner` (FINISH with
an output event, plus its explicit STICKY = 3) and `init_uEnergy_union`
(output event plus its explicit STICKY = 2); `3·NB` is `rankCompute`'s explicit
`rankMultiLookupSpawner`-completion STICKY event plus that spawner's own
output+finish events, once per sync batch. `init_uEnergy_i`,
`rankLookup`/`macroxs`/`microxsAggregator` all pass a NULL output event and
carry no FINISH scope, so the per-lookup and per-gridpoint fan-out contributes
zero events regardless of `U` or `L`.

For the calibrated args (`-s large -g 96 -l 2764800 -b 6912`): `N_i=355`,
`N_g=96`, `U=34080`, `L=2,764,800`, `NB=400`. DBs ≈ `41+355+34080 = 34,476`
(each `uEnergy_grid` leaf is `N_i·4 B = 1.4 KB` — ~48 MB of plane total; the
355 nuclide grids are `96×48 B` each, ~1.6 MB total). EDTs ≈
`17+355+34080+800+8,294,400 = 8,329,652`, overwhelmingly the per-lookup
chains. Events ≈ `27+3·400 = 1,227`, staying small regardless of `L` (only
`NB` moves it). `-l` growth is pure EDT churn (no DB growth); `-g`/`-s` growth grows DB
count *and* size together, and `-s` additionally multiplies the aggregator
fan-in (`num_nucs[fuel]`: 34 small / 321 large).

Counter cross-check: the measured pair predates the move of generation into
its own tasks, so it is a check of the DB column only until it is re-taken
(`calibration pending`). It was verified (1 node, `-s small -g 3 -l 10` vs
`-s small -g 5 -l 20`) against the previous formulas at 252/314/25 and
418/450/25 (`NUM_EDT_CREATE` / `NUM_DB_CREATE` / `NUM_EVENT_CREATE`), with a
runtime baseline of `+1 EDT, +1 DB, +0 EVT` on top of the app totals (the
baseline is the runtime's own bootstrap EDT that invokes `mainEdt` and the
argv DB it hands it — a layer below the app's own `mainEdt`, which the
17-EDT fixed count already includes). The DB column is unchanged by this
cycle; the formulas above now predict 322/314/30 and 488/450/30 for the same
two argument sets (`+N_i+2` EDTs, `+5` events, `N_i = 68` at `-s small`).

## Wiring

`rankLookup` (per lookup) takes `CONST` (→ ARTS RO) deps on the `InputsH`,
`templatesH`, and six *handle* DBs — the `nuclide_grids` GUID array, the
flat `uEnergy` grid, the `uEnergy_grid` GUID array, and the three
materials-handle arrays (`mat_num_nucs`, `mat_nucl_index_list_guids`,
`nucl_concs_list_guids`) — eight dependences in all, none of them the actual
grid payload, only GUID indirections. It binary-searches `uEnergy` locally, then creates
`macroxs` with RO deps on the handle DBs plus the one `uEnergy_grid[idx]`
leaf DB for the energy bucket it landed on. `macroxs` in turn creates
`microxsAggregator`, adding one RO dep per nuclide in the chosen material —
`num_nucs[mat]` individual nuclide-grid leaf DBs. The material is drawn per
lookup, so the fan-in is 4 to 321 at `-s large` (`num_nucs[0]`, fuel, is 321
whenever `n_isotopes != 68`; mean over the material distribution 55.3) and
4 to 34 at `-s small`. `microxsAggregator` is the only EDT that actually reads nuclide-grid
payload.

Every lookup-phase access is RO (`DB_MODE_CONST`); grid/material DBs are
written exactly once during init (one writer task per block, its home decided
by the hint the *creating* task passed) and never touched RW again. Max concurrent RO readers on one nuclide-grid
leaf DB is bounded by the sync-batch width (`b`) and, within that,
by how many concurrently-scheduled lookups happen to draw a material
containing that nuclide (`pick_mat`'s distribution gives material 0, "fuel",
13.9%) — this is data- and schedule-dependent, not statically fixed. The
contention point is therefore the small set of nuclide-grid leaf DBs (`N_i`
of them) crossed against up to `b` concurrently in-flight lookups (6912 at
the calibrated args), not the
per-gridpoint `uEnergy_grid[idx]` DBs (each lookup's `idx` is usually
distinct at these grid sizes).

## Flow

Three sequential program-level phases, each gated by a `FINISH` join:
**init** → **compute** → **finalize**.

Init is a single logical rank and three successive fan-outs. `init_dataH`
builds the object plane — the `N_i` nuclide-grid DBs and the `U`
gridpoint-leaf DBs — and wires the rest of init as one graph, which is the
port's own structure and is left where it is. It writes no element of that
plane: `init_gridsSpawner` (a `FINISH` scope) creates `N_i`
generators, one per nuclide grid, each filling and sorting the one block it
owns from the index-seeded generator; the spawner's output event gates
`init_uEnergy_union`, a single task that reads all `N_i` grids, copies their
energies into the flat `uEnergy` array, sorts it (`O(U log U)`, ~`U·log₂U` ≈
0.5 M comparisons at `U = 34,080`) and prints the grid checksum; its output
event in turn gates the `U`-wide fan-out of `init_uEnergy_i` grid-alignment
tasks under one `FINISH` scope. `init_materials` is independent of all three
and runs concurrently with them. The union step is the one generation step
that stays serial — one task reading `U·48 B` of grid blocks and sorting `U`
doubles — exactly as in the sequential program, and the restructured tier
keeps a per-place copy of it. The compute phase is `NB` strictly serial sync batches: each
`rankMultiLookupSpawner` is a `FINISH` EDT covering up to `b` lookup chains
(up to `b×3` EDTs in flight at the batch's peak); the *next* batch's
`rankCompute` only starts once the previous batch's `FINISH` scope — every
descendant of all `b` chains — has fully drained. For the calibrated args
that is 400 hard synchronization barriers. Within a batch the chains are
spawned serially by the one spawner EDT (create + 8 dependence registrations
per lookup, ~4 µs each), which is the single-node throughput cap — see
Sizing.

`mainEdt`'s only native (non-EDT) work is `read_CLI`/`print_inputs`, which is
negligible; everything else, including grid construction, runs as EDTs.

Nothing but the workload runs inside the timed window: the lookup results are
discarded, so there is no verification pass, and the two upstream per-iteration
progress prints — one per 1000 lookups in the batch spawner, one per 200th
gridpoint in the alignment task — are gone. The only stdout inside the window
is the one-line grid checksum, the input summary, and the closing results
block; the port writes no output file at any setting. Data generation is
index-seeded and parallel (above), so no part of the window is a serialized
input build, and none of it depends on the node count.

## Placement (base)

Every `ocrEdtCreate`/`ocrDbCreate` in this port passes `NULL_HINT`.
Effective policy: **EDTs** → shim round-robin (`ARTS_HINT_ANY_RANK`, atomic
counter modulo rank count); **DBs** → home = creating rank.

The init-phase chain (`globalInit → rankInitSpawner → rankInit → init_rankH →
init_dataH`) is a sequence of 1:1 nested creates, each round-robining
independently, so the grid DBs (all created inside `FNC_init_dataH`) end up
homed on whichever single node that EDT happened to land on — an arbitrary
node, decided by the chain's cumulative round-robin state, not by any
locality intent. The `N_i` generators and the union task round-robin
independently of that, so in base each generator writes a block that is
remote to it; only the hinted tier co-locates writer and block. Because `nprocs` is hardcoded to 1, there is no way to get a
grid replica per node; the grid always lives on exactly one node.

Compute-phase `rankLookup`/`macroxs`/`microxsAggregator` are *also*
independently round-robined, with no relationship to where the grid lives.
Nearly every hop of every lookup chain is therefore a remote acquire of
whichever grid DB it needs — the same worst-case locality pattern as
`fibonacci`, but at payload sizes up to tens of KB per nuclide-grid DB
instead of 4 bytes. At multinode this app is a genuine bandwidth-and-message-rate
stress, by construction, with the intact-but-unexploited locality of the
algorithm (a lookup only ever touches its own material's nuclides) never
expressed in placement.

## Placement (hinted)

As-born round-robins every link of every lookup independently: rankLookup
lands somewhere, spawns macroxs there, which lands somewhere else, which spawns
the aggregator on a third rank — each chain's intermediate results cross the
wire twice for nothing (see above).

The layer is hint arguments only, compiled under
`OCR_APP_OPTIMIZED_PLACEMENT` (`Main.c`; base resolves every constructor to
`NULL_HINT`, and every constructor short-circuits to `NULL_HINT` at one PD,
so base ≡ hinted at the one-node anchor by construction). Five maps, `N` =
`ocrAffinityCount(AFFINITY_PD)`:

| object | home / placement |
|---|---|
| nuclide grid DB `i`, gridpoint leaf DB `i` | `i % N` (`mcSpreadDbHint`) |
| `init_grids_i` EDT `i` (that nuclide grid's writer) | `i % N` (`mcSpreadEdtHint`) |
| `init_uEnergy_i` EDT `i` (that leaf's writer) | `i % N` (`mcSpreadEdtHint`) |
| `init_uEnergy_union` EDT (the `uEnergy` array's writer) | `⌊1·N/9⌋` — that array's own home (`mcStripeEdtHint`) |
| material index/concs DB `j` | `j % N` |
| the nine compute-phase handle blocks, index `k` (a lookup acquires eight of them; the ninth, the rank data handle, is the batch spawner's) | `⌊k·N/9⌋` (`mcStripeDbHint`) |
| `rankLookup` (chain link 1) | **unhinted** — runtime round-robin |
| `macroxs` (link 2) | `idx % N` — the home of the one gridpoint leaf the chain reads (`mcSpreadEdtHint`) |
| `microxsAggregator` (link 3) | the creating rank (`mcChainEdtHint`), i.e. link 2's rank, i.e. the same leaf home |

Two things the layer buys. **Home spreading**: the readers draw a uniformly
random index, so no placement can make the *set* of reads local — but as-born
every grid object is homed on the one rank that ran its init EDT, which then
serves the whole machine. Spreading splits that serving load. A singleton
cannot be split at all, so the nine handle blocks the compute phase acquires
(eight of them per lookup) are
merely distributed — by stride rather than by low index, so their homes cover
the whole rank space instead of ranks `0..8` (at 32 ranks the low-index map
left 23 ranks hosting no handle and piled all nine on top of the material
tables' `j % N` range).

**Chain-to-data placement**: each chain reads exactly one gridpoint leaf, and
reads it *twice* — `macroxs` takes it as a dependence and passes it on to the
aggregator. `idx` is already computed in `rankLookup` at the hint site, so
sending link 2 there is a hint-argument substitution with no extra work, and
link 3 follows for free through the creator pin. The trade is explicit:
one remote EDT creation plus six remote dependence registrations (one-way
sends) in exchange for two acquires that would otherwise be round trips —
under VAL each of those is a re-validation, which is the cost the whole layer
aims at. Link 1 stays round-robin: that is the exact load balance across
lookups, and it is the link holding the eight handle acquires, which are
remote under every map.

Balance of the `idx % N` map, derived rather than assumed: the per-lookup seed
is an arithmetic progression through the port's Lehmer generator, so
`p_energy` advances by a fixed ~1.49e-4 per lookup and `idx` sweeps the
grid with a stride of ~5 points; residues mod `N` are therefore dealt
cyclically, not randomly. Replaying the exact generator, the exact grid build
(`-s large -g 96`, `U = 34,080`) and the exact `grid_search_double`, with
`b = 3456` over 60 batches, gives for links 2/3 (the replay reproduces the
published grid checksum, so the grid it measures is the real one):

| ranks | worst batch, EDT count | cumulative, EDT count | worst batch, work-weighted | cumulative, work-weighted |
|---|---|---|---|---|
| 2 | 1.047 | 1.014 | 1.093 | 1.014 |
| 8 | 1.127 | 1.045 | 1.368 | 1.045 |
| 16 | 1.194 | 1.045 | 1.470 | 1.062 |
| 32 | 1.380 | 1.078 | 1.766 | 1.081 |

"Work-weighted" weights each chain by `num_nucs[mat]`, the aggregator fan-in
that is the chain's actual cost. Link 1 is exactly `b/N`, and no rank is
excluded at any geometry.

On EDT count the map meets R2. On work weight the per-batch figure does not
reach "close to 1" at 16 and 32 ranks, and the decomposition says why: with an
exactly count-balanced control map (`ilookup % N`) the same replay still gives
worst-batch 1.162 / 1.179 / 1.207 / 1.241, because the fan-in is heavy-tailed
(4..321, mean 55.3, σ 107) and one batch offers only `b/N` = 108 chains per
rank at 32. That floor is a property of the workload, not of the map; the
`idx % N` figure is it compounded with the count imbalance
(1.241 × 1.380 = 1.71 ≈ 1.766). The excess is small-sample variance, not
aliasing between `idx % N` and the material draw: cumulatively each rank sees a
fuel fraction of 0.133..0.145 around 0.139 at 32 ranks, and the weighted
cumulative imbalance is 1.081.

Which of the two is operative is settled by the row's own pathology. The
per-batch tail would decide the barrier only if a batch's `b` chains were
co-resident; they are not — the one spawner emits a chain every ~4 µs, so the
machine-wide in-flight count is single- to double-digit and each barrier is
production-limited, not load-limited. For a spawn-limited row the cumulative
column (≤1.081) is the operative quantity and R2 is met on it. This verdict is
conditional on that pathology: a decomposition that parallelises production
(a restructured tier) makes the per-batch column operative again, and there a
count-exact map would be preferable to `idx % N`.

**Writer-to-data placement in init** applies the same rule to the generation
phase: a task that fills one block runs where that block is homed. The `N_i`
generators follow the grid blocks' own `i % N` map, so each generator's single
`RW` acquire is local; the union task follows `uEnergy`'s stripe home, so its
`RW` acquire of the `U·8 B` array is local too. What no map can make local is
the union's fan-in: it reads all `N_i` grid blocks (`U·48 B` in total, 1.6 MB
at the calibrated args) and they are spread by construction, so that acquire
set is remote in the hinted tier and single-homed in base. It is the price of
generating in parallel and it is paid once per run, against the `U·(4+N_i)` ≈
12.1 M dependence registrations of the alignment phase that dominates init.

Rejected: pinning the batch-spawner chain (three acquires per batch —
negligible), and low-index rather than strided handle homes (same per-home
serving load, but clustered).

Earlier measured effect of the *previous* map (creator-pinned chain, low-index
handles) at 2 nodes, `-s large -g 192 -l 65536`: inv_wb compute 28.4→4.66 s
(6.1×), val_wb_nocomb 50.0→37.6 s (1.33×) — compute-phase timer, different
arguments, and superseded by the map above. It is not evidence for the
current layer.

## Sizing (measured)

Every init timing figure in this section and the next is `calibration
pending`: they were measured with generation running serially in one task, and
generation now runs as `N_i` parallel tasks joined by one union task. The
compute-phase figures are unaffected (no compute-phase object, dependence or
placement changed), and the init figures are expected to move only slightly,
since the alignment fan-out — not generation — is what dominates init.

Single-node compute throughput is **spawn-limited**, not worker-limited: the
one live spawner EDT emits a lookup chain every ~4 µs, so 15 workers do
~260K lookups/s while 108 workers do 152K/s — MORE workers are slower,
because the idle workers' steal traffic interferes with the one spawning
worker. `-t` cannot change this (no-op) and the batch width moves it only
marginally (1024↔8192: <3% at one node, −7% at 2 nodes, +5% at 8 —
production, not the window, binds; the calibrated 6912 is the Master/Worker
window rule — twice the largest machine's worker total — not a tuning device). Multinode collapses
~100× further: each chain's
creation and its ~dozens of dependence registrations cross the wire, and
this control-plane traffic — not the grid payload — is the bill. That makes
the app a wiring-plane worst case in every arm, mildly anti-scaling with
node count.

Parameter roles, measured: `-l` is the only pure work dial (linear, zero DB
growth). `-s` selects the H-M configuration — large (the benchmark's
canonical case) changes no structure and not the 1-node rate (261K vs 256K
lookups/s vs small), but sets the fuel fan-in (321 vs 34) and multiplies
init's dependence registrations (`N_i²·g`). `-g` scales the exploded plane
and init linearly and leaves the compute rate untouched at one node; at
multinode the `U`-wide alignment fan-out acquires remotely, so init is
~150 s at 2-8 nodes for `-s large -g 96` (roughly flat in node count,
2× that at g=192, minutes-to-hours at g≥1000 under large). The calibrated
`-g 96` is a feasibility floor, not a host-timeout artifact: at the published
11303 the plane is `U = 4,012,565` gridpoint DBs and init issues
`U·(4+N_i) ≈ 1.44 G` dependence registrations, which no campaign geometry
can hold. `g=96` keeps the exploded 34K-DB plane the row exists to exercise
and leaves the compute phase the majority of the cell. The reduction is
disclosed in the catalog; its *direction* is toward the control-plane-dominated
end, i.e. toward this row's own conclusion, and the paper clause should say so.
Reference points for the disclosure: the code default and the DOE reference
are both `-g 11303`; the app suite's own strong-scaling table publishes
`ss_small/ss_medium` at `-g 1130` and `ss_large` at `-g 11303`
(`third_party/ocr-apps/apps/XSBench/parameters.proposed`), so against the
tightest published tier `-g 96` is a 11.8× reduction, not 118×. `-l
2,764,800` is *inside* the published range (2.76× `ss_medium`'s 1,000,000,
